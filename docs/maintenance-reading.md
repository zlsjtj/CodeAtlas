# 换仓库后，旧请求不应把界面切回去

## 问题

旧的问答处理函数在 `await askRepositoryQuestion(...)` 后直接更新回答，并调用 `setSelectedRepoId(repoId)`。如果用户等待时从 A 仓库切到 B，A 的迟到响应可能把选择切回 A；迟到错误也可能出现在 B 的页面上。

这次修改由代码审阅定位该路径，再为它写浏览器回归；没有把旧版本上的静态分析写成“已复现的用户报告”。

## 可重复的场景

见 [`reading.spec.ts`](../frontend/tests/e2e/reading.spec.ts) 的 `switching repositories drops a late answer`：

1. 用真实后端导入两个临时仓库。
2. 在 A 发起问题，测试拦截请求并延迟返回。这里只用模型替身，不涉及 API 费用。
3. 切到 B，再放行 A 的失败响应。
4. 断言选择仍为 B，源码区为空，且不出现 A 的错误文本。

## 修改

`RepositorySession` 按仓库 ID 分离阅读与改动状态。读取请求使用 AbortController；问答、草案和检查在等待前捕获请求代次，返回时核对是否仍属于当前会话。卸载后即使再切回同一仓库，旧响应也不会重新生效。

文件引用仍使用原有读取接口，受同一排除规则和 200 行限制约束。引用摘录单独保留，当前源码不冒充回答生成时的快照。

## 验证与剩余边界

浏览器回归还覆盖无 Key 导入与索引、符号及关键词搜索、源码翻页、导入失败、读取重试、搜索失败恢复、手机阅读，以及草案预览后明确应用再运行真实 pytest。模型状态只新增布尔字段，测试断言响应中没有 Key。

测试开发中先后遇到了 Next.js 路由提示节点与错误提示共用 `alert`、textarea 定位，以及 Windows 文件换行差异；修正的是测试定位和跨平台断言，没有放宽业务成功条件。

忽略迟到响应只保护当前 UI，不等于取消后端操作。已经确认执行的检查或文件应用可能继续完成；切换仓库不会撤销它们。当前会话历史仅保存在页面内，切换仓库或刷新会清空，不是持久化对话管理。
