# 设计记录

这里记录当前索引、工具调用和 patch 流程的实现取舍。[启动与试用说明](../README.md)在首页。

## 为什么先做行级 chunk

一开始没有直接上向量库，主要是为了把主流程先跑通。这个项目最早要验证的是：仓库能不能导入，文件能不能被索引，模型能不能通过工具找到证据，回答能不能返回路径和行号。

所以当前索引只做了三件事：

1. 跳过 `.git`、`node_modules`、`.next`、`dist` 等噪声目录，以及被文件访问规则排除的路径。
2. 过滤二进制文件和过大的文件。
3. 把文本文件按固定行数切成 chunk，保存相对路径、起止行号、语言和哈希。

这样检索质量不算强，但实现可控，测试也容易写。以后如果改成向量检索或重排，可以复用现有的 `FileChunk` 表结构和工具接口。

## 为什么让模型通过工具读代码

我没有把整个仓库拼进 prompt。仓库一大就会有三个问题：上下文成本高、噪声多、很难追踪模型到底依据了什么。

当前做法是把仓库访问收口到四个工具：

- `list_repo_tree`: 先看目录结构。
- `search_repo`: 通过关键词找候选片段。
- `read_file`: 读取指定文件的行范围。
- `find_symbol`: 查找可能的函数、类或导出符号。

回答时会记录工具名、参数摘要和返回数量。这个记录不复杂，但能让用户复核模型是不是确实读了相关文件。

## 文件排除规则放在哪里

只在扫描时排除文件不够：工具可以按路径直接读取文件，旧索引也可能留下已排除文件的片段。因此索引、目录树、检索、符号定位和 patch 目标读取共用 `RepositoryFilePolicy`。

- 使用 `pathspec` 解析导入目录内各层 `.gitignore`，支持目录范围和 `!` 例外。不读取导入目录之外的规则、全局 Git 配置或 `.git/info/exclude`，已被 Git 跟踪的文件也执行排除规则。
- 默认拒绝 `.env`、`.env.*`、常见私钥及凭据文件、`.ssh` / `.aws` / `.gnupg` 目录。`.env.example`、`.env.sample`、`.env.template` 不在默认拒绝名单中，但仍受 `.gitignore` 约束；`!` 不能放行默认禁止的文件。
- 不跟随符号链接或 Windows 重解析点。如果某层 `.gitignore` 无法读取或解析，其下文件不开放访问。
- 每次请求重新加载规则。新增忽略项后，旧片段立即从搜索和片段接口隐藏；重新索引才会删除对应数据库记录。历史问答、草案、日志和备份不会自动清理。

这是文件访问限制，不是密钥内容扫描或执行沙箱。普通源码、示例配置仍可能含有真实凭据；检查脚本也能读取自身进程有权限访问的文件。

## 为什么 patch 不直接落盘

直接让模型改文件风险太高，尤其是多人协作或用户同时在编辑文件时。当前流程拆成了两步：

1. 先生成完整文件草案和 unified diff。
2. 用户确认后再应用。

应用前会重新读取目标文件，并和草案生成时的 `base_content_sha256` 比较。如果文件已经变了，后端会拒绝写入。批量 apply 也是先全部校验，再开始写文件，避免只写成功一半。

这个方案还有局限：草案依赖模型返回完整文件内容，所以只适合较小文件。更稳的做法应该是结构化 patch 或局部 diff。

## 为什么 checks 用白名单

项目里有“应用并验证”的流程，但我不希望后端执行任意命令。现在只根据仓库结构发现有限命令，例如：

- `python -m pytest tests`
- `npm run typecheck`
- `npm run lint`
- `npm run test`

运行时用固定参数、固定工作目录，并设置超时和输出截断。白名单限制的是命令入口；`npm run test` 和 pytest 仍会执行仓库提供的代码，当前没有执行沙箱，因此只适用于受信仓库。

“应用并检查”的回滚保存并恢复本次写入的目标文件，不撤销测试产生的其他文件、网络请求或外部状态变化。

## 目前测试覆盖的重点

后端测试更关注几类容易出错的地方：

- 仓库路径必须限制在 root 内。
- 忽略规则覆盖直接读取和旧索引，patch 不能绕过文件排除。
- 索引后能通过工具搜索、读取文件、定位符号。
- 问答接口会保存 trace。
- stale patch 会被拒绝。
- 批量 apply 遇到冲突时不会提前写入部分文件。
- checks 失败后，本次写入会被回滚。
- 中英文响应头能影响错误信息和部分输出。

前端加入了 Playwright，使用真实后端验证阅读、切仓库、草案应用和检查入口，见[维护案例](maintenance-reading.md)。问答和草案生成使用模型替身；真实模型的[六道固定问题](../benchmarks/reading-cases.json)尚未运行，不能把自动化测试通过当作问答效果数据。

## 还不够好的地方

- 检索结果排序比较粗糙，复杂问题下容易漏掉相关文件。
- `find_symbol` 不是 AST 解析，只能算轻量定位。
- 后台任务没有持久化队列，服务重启后的恢复能力有限。
- 没有鉴权和多用户隔离，不适合直接暴露到公网。
- 还没有在几个真实项目上系统记录问答效果。

用于模型问答的目录应只包含可以发送给模型服务的代码；文件名过滤不能代替对目录内容的检查。
